# ТЗ — Приложение «Экономика проектов» для Bitrix24

> Источник истины по функциональным требованиям. Сохранён из постановки задачи без изменений
> смысла. При конфликте требований приоритет:
> 1) корректность финансов; 2) сохранность данных; 3) безопасность; 4) функциональные
> требования; 5) UX; 6) визуальные эффекты.

## Критическое требование

Не прототип, не мокап, не набор статических страниц. Реально работающее full-stack приложение
с БД, CRUD, авторизацией через Bitrix24, разграничением прав, финансовыми расчётами, историей
изменений, интеграцией с CRM Bitrix24, demo-mode, тестами, Docker и документацией. Не оставлять
TODO вместо обязательного функционала.

## 1. Исходная задача

Веб-приложение для ручного учёта доходов и расходов по проектам внутри Bitrix24. Совместное
использование несколькими сотрудниками. Главная бизнес-задача — быстро понимать экономическую
эффективность каждого проекта и бизнеса в целом:

- сколько проект должен принести / фактически принёс;
- сколько планировалось потратить / фактически потрачено;
- прибыль, плановая прибыль, рентабельность;
- отклонение план/факт, структура расходов, сотрудники проекта.

Исходные обязательные статьи:
- Доход: **Доход**.
- Расходы: **Внешние программисты**, **Внутренние программисты**, **Расходы на ИИ**,
  **Аренда сервера**, **Дивиденды**.

Пользователи могут сами создавать новые статьи доходов и расходов.

## 2. Формат приложения в Bitrix24

Полноценное приложение Bitrix24, открывается из отдельного пункта левого меню
**«Экономика проектов»**. Работает как iframe-приложение. Ориентир — актуальная официальная
REST API документация Bitrix24. Универсальный CRM API `crm.item.*`, НЕ deprecated `crm.deal.*`.
Scopes минимум: `crm`, `placement`, минимальный для чтения сотрудников (предпочтительно
`user_brief`), `basic` при необходимости проверки пользователя/прав. Избыточные права не
запрашивать.

## 3. Технологический стек

Frontend/Backend: Next.js 16, App Router, TypeScript, React, server-side API/routes.
UI: Tailwind CSS, shadcn/ui, Lucide Icons, Recharts.
Формы: React Hook Form, Zod.
БД: PostgreSQL, Prisma ORM.
Числа: PostgreSQL `DECIMAL/NUMERIC`, Prisma `Decimal`. Все финансовые вычисления на Decimal.
Тесты: Vitest, Testing Library (где полезна), Playwright для ключевых E2E.
Инфра: Docker, Docker Compose, production Dockerfile, PostgreSQL, healthcheck, пример reverse
proxy для VPS.
Качество: ESLint, Prettier, TypeScript strict. Не отключать ошибки через `any`/`@ts-ignore` без
реальной необходимости.

## 4. Deployment

Целевой production — собственный VPS. Два способа запуска:

Локальная разработка:
```
npm install
cp .env.example .env
npm run db:migrate
npm run db:seed
npm run dev
```

Docker:
```
docker compose up --build
```
После запуска приложение доступно без ручного создания таблиц. Production-миграции —
`prisma migrate deploy`. НЕ `prisma db push` как production-механизм.

## 5. Demo Mode (обязательно)

`DEMO_MODE=true` позволяет проверить практически весь функционал без Bitrix24. Заранее
подготовленные: администратор, руководитель, несколько сотрудников; 5–7 проектов (активные и
завершённые; с разной рентабельностью); плановые/фактические доходы и расходы; расходы по часам
и фиксированные; несколько статей; история изменений. Данные реалистичные (например: «Внедрение
CRM „Альфа"», «Поддержка CRM „Север"», «Интеграция 1С — „Вектор"», «Корпоративный портал
„Меридиан"», «AI-ассистент отдела продаж»), не «Test project 1».

Demo-mode позволяет переключать роль (Администратор / Руководитель / Сотрудник) понятным
dev/demo-переключателем. Переключателя нет в production Bitrix24 mode.

## 6. Модель пользователей

Пользователи не создаются вручную — приходят из Bitrix24 (user API). В локальной БД —
snapshot: Bitrix24 User ID, имя, фамилия, фото, активность, локальная роль приложения, время
последней синхронизации. Не дублировать весь профиль.

## 7. Роли

**ADMIN** — админ приложения. Если пользователь — администратор Bitrix24, приложение
автоматически распознаёт его как ADMIN. Полный доступ: все проекты и финансы, создание/
редактирование/удаление/архивирование, категории, сотрудники, роли, журнал изменений, настройки
интеграции. Может назначать роли MANAGER и EMPLOYEE.

**MANAGER** — руководитель. Может: видеть все проекты и все финпоказатели; создавать/
редактировать проекты; добавлять/редактировать/удалять доходы и расходы; добавлять сотрудников
к проекту; работать со статьями; видеть историю. Не может: менять системные настройки
интеграции, назначать ADMIN, управлять установкой приложения.

**EMPLOYEE** — обычный сотрудник. Видит только проекты, где указан участником. Внутри
доступного проекта видит финпоказатели, план, факт, прибыль, рентабельность, операции,
сотрудников, графики. По умолчанию read-only. Не может менять финпоказатели/настройки.

Права всегда повторно проверяются на backend. `GET /api/projects/:id` для не-участника →
`403`.

## 8. Проекты

Создание двумя способами.

**A. Вручную.** Поля: Название (обязательно), Описание, Статус, Дата начала, Дата окончания,
Клиент, внутренний комментарий, сотрудники проекта.

**B. Из Bitrix24 CRM.** Переключатель на форме: `Создать вручную | Выбрать из Bitrix24`.
Минимум: Сделки и Компании. Дополнительно (если без ухудшения основного) — Смарт-процессы.
Deal `entityTypeId = 2`, Company `entityTypeId = 4`. Использовать `crm.item.list` и
`crm.item.get`. После выбора: сохранить ID, тип, snapshot названия; подставить название проекта;
подставить клиента, если однозначно; сохранить домен портала; дать открыть исходную сущность.
На карточке проекта — кнопка `Открыть в Bitrix24 ↗`. CRM — reference, не хранилище финансов.
Финансы — в собственной PostgreSQL.

## 9. Статусы проектов

Обязательные: **Активный**, **Завершён**, **Архив**. Удаление — не основной сценарий,
использовать архивирование. Архивный проект остаётся в БД, сохраняет финансы и историю, не
попадает в список активных по умолчанию. Фильтр: `Активные / Завершённые / Архив / Все`.

## 10. Сотрудники проекта

0..N сотрудников, выбор из реальных сотрудников Bitrix24. Компонент выбора: поиск, фото, имя,
должность (если доступна), multi-select. На карточке проекта — участники аватарами, tooltip
`Имя Фамилия`. На вкладке команды — полный список.

## 11. Финансовая модель

Главная сущность — **FinancialEntry**, строго один проект на запись. Отдельных «общих
расходов» без проекта нет. Показатели компании = сумма доступных проектов.

Поля записи: ID, Проект, Направление (INCOME/EXPENSE), Статья, PLAN/FACT, Дата, Сумма, Валюта,
Комментарий, Автор, Дата создания, Кто изменил, Дата изменения.

Валюта: `RUB`. Мультивалютность не реализовывать. Но `"₽"` не должна быть разбросана по
бизнес-логике — форматирование централизовано.

## 12. Доход

Обязательное: проект, статья дохода, PLAN/FACT, дата, сумма.
Дополнительное: контрагент, номер счёта, дата счёта, комментарий, ссылка на документ,
назначение/описание платежа.
Пустые доп. поля не выводить строками `Контрагент: —`.

## 13. Расход

Поля: проект, статья, PLAN/FACT, дата, способ расчёта, сумма, исполнитель,
контрагент/подрядчик, комментарий, номер документа, ссылка на документ.

## 14. Расчёт расходов программистов

Два режима.
**FIXED** — пользователь вводит сумму.
**HOURS × RATE** — поля «Количество часов», «Стоимость часа»; итог `Сумма = часы × ставка`
(напр. `12.5 ч × 2 000 ₽ = 25 000 ₽`). Frontend показывает расчёт сразу, но окончательное
вычисление обязательно повторяется на backend — сумму с frontend на доверие не принимать.
Для HOURS_RATE сохранять snapshot: `hours`, `hourlyRate`, `calculatedAmount` (чтобы историческая
сумма не менялась при изменении настроек).
Для статей «Внешние программисты» и «Внутренние программисты» режим HOURS_RATE можно предлагать
первым, но FIXED тоже доступен.

## 15. PLAN / FACT

Обязательная часть. У каждой операции `budgetType = PLAN | FACT`. Плановые и фактические записи
хранятся отдельно (не одна запись с `planAmount`+`factAmount`). Допускается опциональная связь
`factEntry → plannedEntry` (не обязательна для создания факта).

## 16. Финансовые формулы

```
Фактический доход   = SUM(FACT INCOME)
Фактические расходы  = SUM(FACT EXPENSE)
Фактическая прибыль  = Фактический доход - Фактические расходы

Плановый доход       = SUM(PLAN INCOME)
Плановые расходы      = SUM(PLAN EXPENSE)
Плановая прибыль      = Плановый доход - Плановые расходы

Рентабельность = Прибыль / Доход × 100%
```
Если доход = 0 → рентабельность `—` (или `null` на backend). Не `Infinity`/`NaN`/`0%`.

Отклонения:
```
Доход:          FACT income  - PLAN income
Расход:         FACT expense - PLAN expense
Прибыль:        FACT profit  - PLAN profit
Рентабельность: FACT margin  - PLAN margin   → показывать в п.п. (напр. "+4.2 п.п."), не "%"
```

## 17. Денежная точность

Деньги — `Decimal(18,2)` или эквивалент. Часы — напр. `Decimal(10,2)`. Никаких `0.1 + 0.2` в
финансовой логике. Формат `1 250 000 ₽` через `Intl.NumberFormat('ru-RU')` или централизованный
formatter.

## 18–22. Главный Dashboard

Основной экран, отвечает на вопрос «Что происходит с экономикой наших проектов прямо сейчас?».
Заголовок «Экономика проектов», подзаголовок «Доходы, расходы и рентабельность проектов».
Справа: период, фильтры, `+ Добавить операцию`, `+ Новый проект`.

**KPI (4 шт.):** Доходы (крупно факт, мелко план + отклонение), Расходы (аналогично), Прибыль
(факт + план), Рентабельность (факт + план + изменение в п.п.). Не рекламные баннеры — цифры
доминируют.

**Графики (минимум 3):**
1. Доходы и расходы во времени за период (факт доходов и расходов, опционально план; line/area/
   аккуратный комбинированный; не 8 линий).
2. Прибыль / рентабельность по проектам (напр. horizontal bar) — видно прибыльные/убыточные.
3. Структура расходов по статьям (donut/chart) + значения/легенда рядом; не только цвет.

**Таблица проектов:** `Проект | Статус | Доход | Расход | Прибыль | Рентабельность | План/факт |
Команда`. Значения — FACT за период. План/факт компактным вторичным значением. Строка
кликабельна → проект. Сортировка: название, доход, расход, прибыль, рентабельность. По
умолчанию — `прибыль DESC` или логичная.

**Фильтры:** период, произвольные даты, проект, статус проекта, сотрудник, статья, PLAN/FACT.
Пресеты периода: Этот месяц, Прошлый месяц, Этот квартал, Этот год, Всё время, Произвольный
период.

## 23. Страница списка проектов `/projects`

Поиск, фильтры, статусы, таблица/качественный список, `Создать проект`. Не бесконечная сетка
огромных карточек.

## 24–25. Карточка проекта `/projects/[id]`

Шапка: Название, статус, клиент, даты, участники, CRM-связь, `Открыть в Bitrix24`,
`Редактировать`. Далее 4 KPI (Доход/Расход/Прибыль/Рентабельность), каждый с plan/fact.

Вкладки: **Обзор** (KPI, plan/fact, динамика, структура расходов, последние операции),
**Финансы** (все операции проекта), **Команда** (сотрудники), **История** (audit log).

## 26. Финансовые операции проекта

Таблица: `Дата | Plan/Fact | Тип | Статья | Описание | Исполнитель | Расчёт | Сумма | Автор | ⋯`.
Для HOURS_RATE: `25 000 ₽` и вторичной строкой `12.5 ч × 2 000 ₽`. Контекстное меню:
Редактировать, Дублировать, Удалить (с подтверждением).

## 27. Общий журнал финансов `/finance`

Все доступные пользователю операции. Фильтры: период, проект, доход/расход, PLAN/FACT, статья,
сотрудник/исполнитель, автор, поиск по комментарию. Сортировка + pagination. Фильтрация/
сортировка/pagination — на backend, не грузить 20 000 записей на frontend.

## 28–29. Статьи `/settings/categories`

Две группы: Доходы, Расходы. Начальные данные — см. п.1. ADMIN/MANAGER может: создавать,
редактировать название, менять цвет, менять порядок, архивировать, удалять неиспользуемую
статью. Если статья использовалась — физическое удаление запрещено, предложить
`Архивировать статью`; исторические операции продолжают отображать её корректно.

Каждая статья имеет `accentColor` из ограниченной палитры (blue, violet, orange, green,
graphite, burgundy, cyan). Цвет — микроакцент (точка, badge, сегмент графика, тонкий
индикатор), не заливка карточки.

## 30. Audit Log

Отдельная сущность **AuditLog**. События минимум: `PROJECT_CREATED`, `PROJECT_UPDATED`,
`PROJECT_ARCHIVED`, `PROJECT_RESTORED`, `FINANCE_CREATED`, `FINANCE_UPDATED`, `FINANCE_DELETED`,
`CATEGORY_CREATED`, `CATEGORY_UPDATED`, `CATEGORY_ARCHIVED`, `USER_ROLE_CHANGED`,
`PROJECT_MEMBER_ADDED`, `PROJECT_MEMBER_REMOVED`. Хранить: ID, portal, actor, action,
entityType, entityId, timestamp, before JSON, after JSON, changedFields.

## 31. Удаление финансовых операций

Soft delete (`deletedAt`, `deletedBy`). После удаления запись не участвует в агрегатах, но факт
остаётся в AuditLog. Пользователь видит `Расход 25 000 ₽ удалён`, админ в истории — кем и когда.

## 32. Страница истории `/history`

ADMIN/MANAGER. Фильтры: период, пользователь, проект, тип события. Вид человекочитаемый:
```
Сегодня, 14:32
Иван Петров
изменил расход проекта «Альфа»
25 000 ₽ → 32 000 ₽
```
Не показывать сырой JSON пользователю (JSON — для БД/диагностики).

## 33–36. Дизайн

Не как admin panel / Bootstrap / типовой shadcn demo / стандартный Bitrix24 / дешёвый SaaS с
20 карточками. Направление: **Apple** (чистота, типографика, пространство, точная иерархия,
крупные спокойные цифры, минимум шума, premium feel, читаемость). Референсы:
**alente.ru/krsk** (типографика, сетка, whitespace, editorial rhythm),
**chipsa.ru** (графичность, минимализм, контраст, характер). Не копировать сайты.

Дизайн-система: фон `#F5F5F7`/тёплый off-white; карточки `#FFFFFF`; текст `#111111`; вторичный
— neutral gray; border — спокойный серый; один фирменный акцент (cobalt/indigo), не заливать
им интерфейс. Семантика: positive — muted green, warning — amber, negative — controlled red.
Радиусы ~14–22 px. Тени очень мягкие. Избегать glassmorphism, neon, огромных blur, gradient
everywhere, сильных drop shadows.

Типографика: system-first (`-apple-system, BlinkMacSystemFont, "SF Pro Display", "SF Pro Text",
Inter, sans-serif`). Нелицензионные SF Pro в репозиторий не класть. Иерархия: page title
крупный; KPI — очень заметные цифры; labels маленькие и спокойные.

Таблицы: чистые, удобные, сортируемые, hover-state, sticky header при необходимости, адекватная
ширина столбцов, без десяти вертикальных border.

## 37–40. Состояния

Empty states — не пустой белый блок, а заголовок + пояснение + кнопки действий. Loading —
skeleton, не прыгающая страница. Error states обязательно обработать: Bitrix24 API недоступен,
токен просрочен, нет прав, проект не найден, CRM-сущность удалена, сеть недоступна, backend
validation error, база недоступна. Сообщения человеческие, не `PrismaClientKnownRequestError
P2002`. Toasts после действий (`Доход добавлен`, `Расход обновлён`, `Проект отправлен в архив`,
`Статья создана`). Destructive actions — confirmation dialog.

## 41. CRM интеграция — service layer

Отдельный слой `src/lib/bitrix/` (client.ts, auth.ts, users.ts, crm.ts, types.ts). Никаких
`fetch('https://xxx.bitrix24.ru/rest/...')` разбросанных по компонентам.

## 42. OAuth / безопасность Bitrix24

Токены — секреты. Нельзя: логировать AUTH_ID/REFRESH_ID, отдавать refresh token на frontend,
хранить секреты plaintext без необходимости. Проверять контекст вызова приложения. На
production: токены зашифрованы (`APP_ENCRYPTION_KEY`, AES-256-GCM или эквивалент), server-side
Bitrix client.

## 43. Multi-portal

Не привязывать БД к одному hardcoded домену. Сущность `PortalInstallation` (id, memberId,
domain, applicationToken, createdAt, updatedAt). Пользователи, проекты, роли и категории
принадлежат конкретному порталу.

## 44. Сессия приложения

После валидного запуска из Bitrix24 определить portal, current Bitrix user, app role. Backend
не верит клиентскому `{userId, role}`. Роль определяет сервер. Для iframe — корректная cookie
policy: HttpOnly, Secure, подходящий SameSite для iframe, ограниченный срок. Mutation endpoints
защитить от CSRF/replay.

## 45–48. Prisma-модель

Минимум: `PortalInstallation`, `AppUser`, `Project`, `ProjectMember`, `FinanceCategory`,
`FinancialEntry`, `AuditLog`. Дополнительно при необходимости: `BitrixCredential`, `Session`.

**Project:** id, portalId, name, description, clientName, status, startDate, endDate,
sourceType, crmEntityType, crmEntityTypeId, crmEntityId, crmEntityTitle, createdById, createdAt,
updatedById, updatedAt, archivedAt, archivedById. Статус — enum, не произвольная строка.

**FinancialEntry:** id, portalId, projectId, categoryId, direction, budgetType, calculationMode,
operationDate, amount, hours, hourlyRate, employeeId, contractorName, counterpartyName,
invoiceNumber, invoiceDate, documentUrl, description, comment, plannedEntryId, createdById,
createdAt, updatedById, updatedAt, deletedAt, deletedById.

Индексы минимум: `portalId`, `projectId`, `operationDate`, `budgetType`, `direction`,
`categoryId`, `deletedAt` + составные для частых финансовых выборок. Без premature optimization.

## 49. Серверная финансовая логика

Отдельный domain/service модуль `src/domain/finance/` (calculations.ts, aggregates.ts,
types.ts). Единый источник истины для формул — не дублировать в Dashboard/Project page/API/
chart.

## 50. Backend API

REST-style routes или Server Actions там, где оправдано. Прозрачная архитектура. Логические
операции минимум: GET projects, GET project, POST project, PATCH project, ARCHIVE project;
GET/POST/PATCH/DELETE financial entries; GET dashboard aggregates; GET/POST/PATCH/(DELETE|
archive) categories; GET users; GET audit; GET Bitrix CRM entities.

## 51. Validation

Server-side Zod. Сумма `> 0`, часы `> 0`, ставка `>= 0`. При `HOURS_RATE` поля hours и rate
обязательны; при `FIXED` не влияют на сумму. Дата окончания проекта не раньше даты начала.

## 52. Атомарность

Изменение финансовой записи + создание audit — в одной DB-транзакции. Не допускать «финанс
изменился, audit не записался».

## 53. Dashboard performance

Без N+1 (`projects.forEach(project => отдельный SQL)`). Агрегаты — эффективными queries/groupBy.

## 54. Data access

Каждый query учитывает `portalId`. Пользователь портала A не может получить проект портала B по
ID.

## 55–57. Ввод

Форма добавления финансов быстрая. Порядок: Income/Expense → Plan/Fact → Проект → Статья → Дата
→ Сумма либо hours/rate → доп. поля (спрятаны за `Дополнительные данные`). Не форма из 18
обязательных полей. Из проекта `+ Расход` — проект уже выбран. Основные фильтры списков
синхронизировать с query params (`/finance?project=15&type=EXPENSE&from=...&to=...`).

## 58. Accessibility

Keyboard navigation, focus states, labels, aria-label для icon-only кнопок, достаточный
контраст, «прибыль/убыток» не только цветом.

## 65. Unit tests финансов (обязательно)

- Прибыль: Income 1 000 000, Expenses 700 000 → Profit 300 000.
- Рентабельность: → 30%.
- Нулевой доход: Income 0, Expenses 100 000 → Margin null.
- Убыток: Income 500 000, Expenses 700 000 → Profit −200 000, Margin −40%.
- Hourly: 12.5 × 2000 = 25 000.
- Decimal: кейс, подтверждающий отсутствие floating point ошибки.
- Deleted: удалённая операция не в aggregate.
- PLAN/FACT: независимые суммы.

## 66. Permission tests (обязательно)

- Employee, участник Project A: GET Project A → 200.
- Employee, не участник Project B: GET Project B → 403.
- Employee mutation: POST financial entry → 403.
- Manager: GET all projects → 200; POST finance → 200.
- Admin: settings → 200.

открывает проект → проверяет прибыль → проверяет рентабельность → редактирует расход →
проверяет изменение показателей → открывает историю → видит запись изменения.

# Design — «Экономика проектов» (Bitrix24 app)

Date: 2026-09-08
Status: Approved (chat), 2026-09-08
Requirements: `docs/REQUIREMENTS.md` (78-point ТЗ, source of truth)

## 1. Goal

Full-stack Bitrix24 iframe application for manual plan/fact income & expense tracking per
project, giving management a live read on project- and company-level economics: profit, margin,
plan/fact deviation, expense structure, team.

## 2. Approach

Single Next.js (App Router) application, own PostgreSQL as the financial system of record,
Bitrix24 as identity + CRM reference only. One cohesive project (not decomposed) built in the
16 phases of ТЗ §77. Demo-mode is the primary verification path (no live Bitrix portal
available); Bitrix integration is implemented fully against the official REST API but not
live-tested this cycle.

## 3. Decisions (ADR seeds -> docs/DECISIONS.md)

- **ADR-001** PostgreSQL, not SQLite — multi-user, production VPS, `DECIMAL`, concurrent writes.
- **ADR-002** Separate PLAN / FACT `FinancialEntry` rows — cleaner history, date handling,
  analytics; optional `plannedEntryId` link on a FACT row.
- **ADR-003** Soft-delete financial entries (`deletedAt`/`deletedById`) — financial audit;
  excluded from aggregates, still visible in audit log.
- **ADR-004** Bitrix24 = identity/CRM reference; PostgreSQL = financial storage. CRM entity is
  linked by snapshot (id/type/title), never the source of money.
- **ADR-005** Next.js 16 targeted; fall back to latest stable 15.x only if 16 blocks the build.
  (Record actual version chosen.)
- **ADR-006** Stateless signed session cookie (`jose`, HS256, `SESSION_SECRET`) carrying
  `{portalId, appUserId, role, demo?}`. No `Session` table. Role is re-resolved / re-checked
  server-side on every protected request; the cookie is a convenience, not an authority.
- **ADR-007** Bitrix OAuth tokens encrypted at rest with AES-256-GCM (`APP_ENCRYPTION_KEY`,
  32-byte base64). Stored on `PortalInstallation`. Never logged, never sent to the client.
- **ADR-008** CSRF: double-submit token — non-`HttpOnly` `csrf` cookie + `x-csrf-token` header
  required on all mutating requests; enforced in a shared handler wrapper. Session cookie
  `SameSite=None; Secure; HttpOnly` for iframe embedding.
- **ADR-009** Money as `Prisma.Decimal` end-to-end; the finance domain module accepts and
  returns `Decimal` (or `null` for undefined margin). `decimal.js` config: 40 significant
  digits, `ROUND_HALF_UP`.
- **ADR-010** Multi-tenancy via a mandatory `withPortal(portalId)` data-access helper; every
  Prisma query for portal-owned data goes through it. Enforced by convention + integration test.
- **ADR-011** Integration tests run against a real PostgreSQL (Docker, `docker-compose.test.yml`
  or a `TEST_DATABASE_URL`), schema pushed once, per-test truncation + targeted seed.
- **ADR-012** Dashboard default period preset: **"Этот год"** (more visible signal on demo
  data). All presets per ТЗ §22.
- **ADR-013** README screenshots generated by a Playwright script in demo-mode against a built
  app, committed under `docs/screenshots/`.

### Contract highlights

- `domain/finance` never imports Prisma. Route handlers load rows via `withPortal`, map to
  `EntryInput` (plain `{direction, budgetType, amount: Decimal, categoryId, operationDate,
  deletedAt}`), pass arrays in. Deleted rows are filtered inside `aggregates` (single choke
  point) — callers may pass everything.
- `margin(income, profit)` returns `null` iff `income.isZero()`. Formatter renders `null` as
  `—`. API serializes `null`.
- `hoursRateAmount(hours, rate)` = `hours.mul(rate)` rounded to 2dp; route handler recomputes
  this server-side and ignores any client `amount`/`calculatedAmount` for `HOURS_RATE`.
- Every mutating handler wraps `prisma.$transaction([...mutation, audit])`.

## 5. Data model (Prisma)

Enums: `AppRole {ADMIN,MANAGER,EMPLOYEE}`, `ProjectStatus {ACTIVE,COMPLETED,ARCHIVED}`,
`ProjectSource {MANUAL,BITRIX_CRM}`, `CrmEntityType {DEAL,COMPANY,SMART_PROCESS}`,
`FinanceDirection {INCOME,EXPENSE}`, `BudgetType {PLAN,FACT}`,
`CalculationMode {FIXED,HOURS_RATE}`, `CategoryKind {INCOME,EXPENSE}`,
`AuditAction {PROJECT_CREATED,...}` (full list ТЗ §30).

Entities: `PortalInstallation`, `AppUser`, `Project`, `ProjectMember`, `FinanceCategory`,
`FinancialEntry`, `AuditLog`. Fields per ТЗ §45–47. Money `Decimal @db.Decimal(18,2)`, hours /
hourlyRate `Decimal @db.Decimal(10,2)`. Indexes per ТЗ §48 incl. composite
`(portalId, projectId, budgetType, direction, deletedAt)` and `(portalId, operationDate)`.

Scoping: every portal-owned model has `portalId` + relation to `PortalInstallation`; unique
keys are composite with `portalId` (e.g. category `@@unique([portalId, kind, name])`,
`AppUser @@unique([portalId, bitrixUserId])`).

## 6. Auth & session

- **Demo:** `GET /` with `DEMO_MODE=true` and no session → issue cookie for the seeded demo
  admin; a header control switches `role` (and identity for EMPLOYEE) by re-issuing the cookie.
  Switch endpoint refuses when `DEMO_MODE!=true`.
- **Production:** Bitrix install handler stores `PortalInstallation` (+ encrypted tokens).
  Placement handler validates the signed Bitrix request, resolves the Bitrix user via
  `user.current`, upserts `AppUser` snapshot, resolves role (`is_admin` → ADMIN, else stored
  role, else EMPLOYEE), issues the session cookie, renders the app.
- `resolveSession` is called by every protected handler; role/permissions are recomputed from
  the DB `AppUser`, not trusted from the cookie payload alone.

## 7. Permissions matrix (enforced server-side — ТЗ §7, §66)

| Capability | ADMIN | MANAGER | EMPLOYEE |
|---|---|---|---|
| View all projects | ✓ | ✓ | only member-of |
| View project financials | ✓ | ✓ | ✓ (within accessible project) |
| Create / edit project | ✓ | ✓ | ✗ |
| Archive / restore project | ✓ | ✓ | ✗ |
| Create / edit / delete finance entry | ✓ | ✓ | ✗ |
| Manage project members | ✓ | ✓ | ✗ |
| Manage categories | ✓ | ✓ | ✗ |
| View history | ✓ | ✓ | ✗ (own project overview only) |
| Assign MANAGER/EMPLOYEE roles | ✓ | ✗ | ✗ |
| Integration / install settings | ✓ | ✗ | ✗ |

`GET /api/projects/:id` for a non-member EMPLOYEE → `403`. Any finance mutation by EMPLOYEE →
`403`.

## 8. Testing

- **Unit (Vitest):** finance domain — all ТЗ §65 cases; percent/money formatters; permission
  predicate table (ТЗ §66 logic level).
- **Integration (Vitest + real PG):** route handlers via `fetch`/handler invocation with a
  seeded portal — permission matrix returns correct 200/403; portal isolation (portal A user
  cannot GET portal B project by id); mutation+audit atomicity (forced audit failure rolls back
  the mutation); soft-deleted entry drops out of `GET dashboard aggregates`.
- **E2E (Playwright):** ТЗ §67 scenario end to end in demo-mode.
- Also: `docs/TESTING.md` documents unit/integration/e2e/manual matrices.

Excel export, notifications, Telegram, employee comments, WebSockets.

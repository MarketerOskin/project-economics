# Архитектурные решения (ADR)

## ADR-001 — PostgreSQL, не SQLite

Приложением совместно пользуются несколько сотрудников, целевой деплой — VPS с
несколькими воркерами. Нужны конкурентные записи, `DECIMAL/NUMERIC`, `$transaction`,
составные индексы. SQLite для этого не подходит.

## ADR-002 — PLAN и FACT как отдельные записи `FinancialEntry`

Не `planAmount` + `factAmount` в одной строке. Отдельные записи дают честную историю
(когда именно внесли план, когда факт), корректную работу с датами и периодами,
возможность связать конкретный факт с планом (`plannedEntryId`) и простую агрегацию
`SUM ... WHERE budgetType = ...`.

## ADR-003 — soft-delete финансовых операций

`deletedAt` / `deletedById`. Удалённая операция не участвует ни в одном агрегате
(единая точка фильтрации — `src/domain/finance/aggregates.ts`), но остаётся в БД и в
`AuditLog`: аудит финансов важнее экономии места. Пользователь видит «Расход 25 000 ₽
удалён», администратор в истории — кем и когда.

## ADR-004 — Bitrix24 = identity + CRM-справочник, PostgreSQL = хранилище финансов

CRM-сущность связывается снимком (`crmEntityId` / `crmEntityType` / `crmEntityTitle` /
`crmEntityUrl`), а не является источником денег. Это устойчиво к изменению/удалению
сущности в CRM и не создаёт зависимости расчётов от доступности Bitrix24.

## ADR-005 — Next.js 16 (stable), Prisma 6.19

Next 16.3.4 — актуальный stable на момент разработки. Prisma **6.19.3**, а не 7.x:
Prisma 7 переводит конфиг на ESM `prisma.config.ts`, что ломает автозагрузку `.env`
(нужен явный `dotenv/config`) и добавляет миграционную возню без выгоды для этого
проекта. Prisma 6 — зрелый инструментарий, стабильная генерация клиента.
`prisma` вынесен в `dependencies` — чтобы `prisma migrate deploy` работал внутри
контейнера.

## ADR-006 — Stateless подписанный session-cookie (`jose`, HS256)

Cookie несёт `{portalId, appUserId, role, demo}`, срок 8ч. Таблицы `Session` нет.
**Роль в cookie — только подсказка**: любой защищённый обработчик повторно определяет
роль из свежей записи `AppUser` (`isBitrixAdmin → ADMIN`, иначе `AppUser.role`).
Подделанная роль в cookie игнорируется (есть тест).

## ADR-007 — Токены Bitrix24 шифруются AES-256-GCM

`APP_ENCRYPTION_KEY` (base64, 32 байта). Формат `iv.tag.ciphertext`. Токены никогда не
логируются (`redactTokens` в клиенте), не отдаются на фронтенд, при `expired_token`
клиент один раз обновляет и перезаписывает зашифрованные токены.

## ADR-008 — CSRF: double-submit token

Не-`HttpOnly` cookie `pe_csrf` + заголовок `x-csrf-token` на всех не-GET запросах,
проверка в `route()`. Session-cookie в production — `SameSite=None; Secure; HttpOnly`
(нужно для iframe в Bitrix24).

## ADR-009 — Деньги — `Decimal` от края до края

`Prisma.Decimal` (decimal.js), 40 значащих цифр, `ROUND_HALF_UP`. Домен финансов
принимает и возвращает `Decimal` (или `null` для неопределённой рентабельности).
`number` в финансовой логике не используется; в форматтере `toNumber()` — только для
отображения (точно для всех реалистичных сумм).

## ADR-010 — Мультитенантность через обязательный `withPortal(portalId)`

Каждый портал-owned запрос идёт через фасад, который подставляет `portalId` в `where`
и `data`. `findByIdOrThrow` отдаёт 404 для строки чужого портала. Проверяется
интеграционным тестом изоляции.

## ADR-011 — Интеграционные тесты — на реальной PostgreSQL

`docker-compose.test.yml` (порт 5433), `prisma migrate deploy`, truncate + точечный
сид перед каждым тестом. Права и изоляция порталов проверяются на настоящих
HTTP-обработчиках, а не на моках.

## ADR-012 — Пресет периода дашборда по умолчанию — «Этот год»

На демо-данных даёт больше видимого сигнала, чем «Этот месяц». Все пресеты — по ТЗ §22.

## ADR-013 — Committed light theme

Приложение живёт внутри Bitrix24 на десктопе. Одна выверенная светлая тема (фон
`#F5F5F7`, карточки белые, один кобальтовый акцент) вместо half-baked тёмной.
Палитра категорий — из валидированной CVD-безопасной data-viz палитры.

## ADR-014 — `typedRoutes` выключен

Навигация строится динамически из конфигов и query-строк; `typedRoutes` требовал бы
`as Route` в десятке мест. Каждый маршрут покрыт интеграционным тестом.

## ADR-015 — Ручной биллинг (оператор), не платёжный шлюз

Marketplace-приложение ещё не опубликовано (нужна модерация Bitrix), своего платёжного
провайдера подключать рано. `PortalInstallation.plan`/`planExpiresAt` — минимальная
модель тарифа; отдельная роль «оператор» (не через Bitrix, своя cookie-сессия,
credentials из env — `src/lib/operator/`) вручную выдаёт Pro тем, кто оплатил вне
приложения. Каждая выдача логируется в `OperatorGrant` (кто/когда/до какой даты).
Заменить на автоматический биллинг (Marketplace `app.info`/`ONAPPPAYMENT` или свой
эквайринг) можно позже без изменения гейтов — они читают только `session.plan`.

## ADR-016 — Оператор — отдельный auth-контур, не роль ADMIN

Оператор управляет ЧЕРЕЗ порталы (может выдать Pro любому), поэтому не может быть ролью
внутри одного портала — это дало бы владельцу одного клиентского аккаунта доступ к
чужим данным. Отдельная cookie (`pe_operator_session`), отдельный JWT payload без
`portalId`, отдельный серверный пайплайн (`routeOperator`, не `route`). Пароль —
`scrypt` через `node:crypto` (без новой зависимости), один аккаунт из `.env`.

## ADR-017 — Продажи: заявка на Pro внутри приложения, не внешняя форма

`UpsellNotice` (заблокированная функция) вела в никуда — просто текст «доступно на
Pro». Добавлена страница `/pricing` (Free/Pro сравнение) с формой заявки
(`ProLead`: контакт + комментарий, один открытый лид на портал — повторная отправка
при открытой заявке даёт 409, а не тихий дубль). Заявка появляется во вкладке
«Заявки на Pro» в `/operator`: оператор видит домен портала, кто и что написал, и
может в один клик «Выдать Pro» (грант + перевод заявки в CONVERTED одной операцией)
или отметить «Связался»/«Отказ». Демо-портал исключён из счётчика «N на Pro» в
`getOperatorOverview` — он не платящий клиент, даже если ему выдан план PRO в БД
(и без выдачи он и так видит Pro-функционал через `isDemo`-обход в `resolveSession`).

## ADR-018 — Онбординг: реальные данные, не ручной чек-лист

Шаги («есть проект», «есть участник», «есть операция») считаются прямо из БД
(`getOnboardingProgress`), а не хранятся как отдельные булевы флаги, которые можно
было бы поставить не по делу. Единственное персистентное состояние —
`onboardingDismissedAt` (когда явно скрыли), чтобы чек-лист не вернулся уже
работающему с приложением порталу после того, как он его закрыл. Демо-портал
исключён — он не проходит установку и не нуждается в первом шаге.

## ADR-019 — Путь монетизации: прямые продажи → агентский договор, не revenue-share

По факту прочтения подписанных документов (`Лицензионный договор с разработчиком`,
`Условия использования каталога решений`, `Агентский договор`) revenue-share-модель,
к которой ИП уже присоединился (Соглашение №29181052), не подходит для нишевого
инструмента: вознаграждение считается по «коэффициенту использования» относительно
**всех** платных приложений на портале, купивших единый Сертификат
1С-Битрикс24.Маркетплейс — доход размыт чужими приложениями и не поддаётся контролю
цены. При revenue-share платный функционал вообще не должен резаться пейволлом (чем
больше пользуются — тем больше платят через Битрикс), то есть весь `/pricing` +
`/operator` для этой модели просто не нужен.

Решение (бизнес-выбор владельца продукта, зафиксирован 2026-09-16):
1. **Сейчас** — продавать напрямую, как уже реализовано: `/pricing` → заявка →
   `/operator` выдаёт Pro вручную. 100% маржи, ноль зависимости от модерации
   Маркетплейса, можно продавать уже сегодня.
2. **После первых платящих клиентов** — публикация в Каталог решений по
   **агентскому договору** (не по уже подписанному лицензионному): своя цена
   («Цена Приложения»), Битрикс — платёжный агент (20% вознаграждения агента, 80%
   ИП), приём оплаты и генерация «ключей доступа» — на стороне Битрикса. Это
   отдельный договор, не автоматически включённый Соглашением №29181052 — нужно
   отдельное присоединение через Личный кабинет с УКЭП (действие только владельца
   ИП, не автоматизируется).

Технические последствия шага 2 (не начаты, не нужны до появления живого спроса):
- гейты `requirePro()` переключаются с `session.plan` (наша БД) на факт активного
  ключа доступа/сертификата от Битрикса;
- `/pricing` перестаёт быть формой заявки и становится витриной с переходом в
  оплату через интерфейс Битрикс24 (Цена Приложения задаётся в Личном кабинете, не
  у нас в БД);
- `/operator` и ручная выдача Pro остаются как резервный/прямой канал продаж мимо
  каталога — агентский договор не обязывает продавать исключительно через Битрикс;
- нужен текст Пользовательского соглашения по форме Приложения №1 к условиям
  каталога и опубликованная политика обработки персональных данных — сейчас есть
  только проприетарная `LICENSE` для тестового задания, для реальных клиентов
  каталога нужен отдельный документ.

## ADR-020 — Домен: поддомен сайта интегратора, не отдельная покупка

`economics.toxick.ru` вместо нового домена — `toxick.ru` уже живёт на том же VPS
(159.194.205.246, тот же сервер, что демо и `life-crm`), поддомен ничего не стоит и
не требует переноса DNS основного сайта. A-запись у регистратора (reg.ru), сертификат —
Let's Encrypt через `certbot --nginx`, отдельный от сертификата `toxick.ru`. `APP_URL`
переключён на `https://economics.toxick.ru` — обработчик и установка Bitrix24 требуют
HTTPS, по IP без домена это было невозможно.

Побочный эффект: cookie-политика приложения глобальная (одна на инстанс, зависит от
`APP_URL`), поэтому старая ссылка на демо по голому IP (`http://159.194.205.246`)
больше не годится для входа — сессионная cookie теперь всегда `Secure`, по HTTP её
не примет браузер. Канонический адрес отныне только `https://economics.toxick.ru`.

## ADR-021 — Требования модерации Маркетплейса: монетизация, логи, очистка данных

Сверка с «Порядком публикации» и «Требованиями к оформлению» (apidocs.bitrix24.ru,
редакция от 18.09.2026) изменила часть ADR-019:

1. **Статус решения и платный Pro.** «Немонетизируемым» может быть только решение без
   оплаты своего функционала (п. C.iii–iv), поэтому в каталоге мы «Монетизируемое».
   Допплату за *дополнительный* функционал документация разрешает принимать самостоятельно
   (monetization/in-app-purchases.md), но первая формулировка карточки («Pro — проекты без
   лимита, оплата напрямую по счёту») была отклонена модерацией: платили за само решение,
   а бесплатная часть (3 проекта) выглядела как демо. Итог: лимит проектов **снят**
   (`FREE_LIMITS` удалён), Free — полноценный продукт; Pro = только дополнительный
   функционал (сейчас импорт из CRM), «приоритетная поддержка» из состава Pro убрана.
   Механизма «оплата за отдельную функцию через Битрикс с ключом доступа» в актуальной
   документации не найдено — «Настроить продажи» там про реквизиты для выплат по подписке.
2. **Логи REST-вызовов ≥ 3 суток** (требование к серверным решениям): таблица
   `ApiCallLog`, пишется в `callBitrix`/`callBitrixWithToken`, токены вырезаются
   (`redactTokens`, в т.ч. JSON-ключи), поля обрезаются до 4000 символов, хранение 7 дней,
   очистка — попутно при записи, не чаще раза в час (без cron). Сбой записи лога никогда не
   ломает сам вызов.
3. **Удаление приложения.** Подписка на `ONAPPUNINSTALL` через `event.bind` теперь делается
   при установке (раньше — только ручной шаг из README, событие до нас не доходило).
   `data[CLEAN]=1` («Очистить данные приложения») стирает весь портал явными удалениями в
   транзакции (`purgePortalData`; `FinancialEntry→FinanceCategory` — RESTRICT, каскад
   от портала ненадёжен). `CLEAN=0` — как раньше: токены сброшены, данные остаются для
   повторной установки.

## ADR-022 — Возврат лимита Free (3 проекта) и графиков как платного функционала

ADR-021 п.1 убрал `FREE_LIMITS`, посчитав лимит проектов причиной отказа модерации. Реальная
причина оказалась другой: модератор указал на способ оплаты («напрямую по счёту, не через
Маркетплейс»), а не на сам факт лимита — документация прямо разрешает «наличие лимитов;
платные расширения; дополнительные тарифы» (raw.githubusercontent.com/bitrix-tools/
b24-rest-docs, market/monetization/index.md, «Критерии статуса Монетизируемое», п.3), если
бесплатная часть остаётся «реальным, полезным сценарием».

Решение (владелец продукта, 2026-09-22): вернуть лимит и расширить платный функционал —
он звучал слабо как единственный повод для подписки (разовый импорт из CRM не тянет на
1000 ₽/мес).

- `FREE_LIMITS.maxActiveProjects = 3` восстановлен, гейт в `POST /api/projects` — как было.
- Графики (`timeseries`, `expenseStructure`, `projectBars`) стали Pro-only: гейт — в
  `loadDashboard(scope, actor, plan, q)` (аргумент `plan` теперь обязателен), а не только
  на фронтенде — прямой вызов `/api/dashboard` с Free-планом получает пустые массивы, не
  цифры. KPI-карточки и список проектов остаются бесплатными — free-сценарий рабочий, не
  демо-версия.
- Оплата за Pro — «встроенные покупки» (in-app purchases): по указанию модератора нужно
  отметить чекбокс «Содержит встроенные покупки» в карточке решения и описать бесплатную
  и платную часть одним абзацем/предложением, а не как два параллельных тарифа.

## ADR-023 — Сессионная cookie: добавлен атрибут Partitioned (CHIPS)

На новом тестовом портале `it-wizards.bitrix24.ru` установка снова обрывалась: install
отдавал 307 с корректным `Set-Cookie` (`Secure; SameSite=None`), портал создавался в БД
(`isActive=true`), но следующий же `GET /api/session` внутри iframe получал 401 — куки не
доехали. Подтверждено по nginx-логам продакшена, не гипотеза.

Причина: `SameSite=None; Secure` разрешает третьесторонние cookie технически, но не
отменяет отдельную политику браузера блокировать НЕ партиционированные third-party cookies
целиком (Chromium/Yandex Browser). Стандартное решение — CHIPS: атрибут `Partitioned`
scoping cookie по паре (сайт верхнего уровня, наш ориджин), а не блокирует её. Next.js уже
поддерживает `partitioned` в опциях `res.cookies.set()`.

`sessionCookieOptions()`/`csrfCookieOptions()` теперь возвращают `partitioned: secure`
(true на https-проде, false на http-деплое, где Secure-куки всё равно недопустимы).
Тест на реальный `Set-Cookie` из install-роута проверяет наличие `Partitioned`.

## ADR-024 — Сессия внутри iframe: не только cookie, запасной путь через токен в URL

`Partitioned` (ADR-023) не помог. Прямой тест на проде (временное логирование `$http_cookie`
и `$sent_http_set_cookie` в nginx, включалось и выключалось на 2 минуты) показал: сервер
корректно отдаёт `Set-Cookie` с `Secure; SameSite=None; Partitioned`, но браузер (YaBrowser
внутри iframe Bitrix24) не сохраняет и не присылает её вообще — ни разу, независимо от
атрибутов. Отдельно проверено: собственный CSP (`frame-ancestors`) корректно не даёт
встроить приложение в посторонний источник — значит воспроизвести это через произвольный
iframe нельзя, тестировали только через временный demo-режим на проде (тоже включали и
выключали на пару минут). Вывод: в этом браузере сторонние cookie в iframe блокируются
полностью, cookie-путь для сессии не спасти никакими атрибутами.

Решение: `issueSession()` при редиректе (install/handler/demo-bootstrap) кладёт подписанный
токен ещё и в query (`?pe_token=`), не только в cookie. `proxy.ts` на каждый запрos:
если есть `pe_token` в URL или заголовок `x-pe-session`, а cookie нет — переносит токен
в `req.cookies` того же прохода (документированный приём Next.js: mutating `request.cookies`
+ `NextResponse.next({request:{headers}})` делает значение видимым для `cookies()` в Server
Components и `req.cookies` в `route()` без изменений там) и пытается поставить настоящую
cookie на будущее (не вредит, если браузер её всё равно проигнорирует).

На клиенте (`lib/client/token-bridge.ts`, подключено в `SessionProvider` через
`useLayoutEffect`, раньше остальных эффектов): токен из `?pe_token=` уходит в `localStorage`
(хранилище самого iframe, third-party-блокировки на него не действуют) и вычищается из
адресной строки; глобальный `window.fetch` патчится один раз на вкладку, чтобы подставлять
заголовок `x-pe-session` на все запросы к своему origin — это ловит и наши `apiFetch`-вызовы,
и внутренние fetch-переходы роутера Next.js между страницами.

CSRF: двойная отправка через cookie (`pe_csrf`) точно так же не доедет в этом браузере.
Раз собрать заголовок `x-pe-session` может только JS с нашего origin (localStorage чужому
сайту не виден), присутствие этого заголовка само по себе доказывает не-межсайтовый запрос —
`route()` пропускает CSRF-проверку, когда он есть, оставляя её как раньше для обычных
cookie-браузеров.

Компромисс: токен живёт в `localStorage`, а не только в `HttpOnly`-cookie — при XSS его можно
будет прочитать. Это стандартный, широко используемый в приложениях для Bitrix24 компромисс
именно под эту проблему платформы.

## ADR-025 — Админ-флаг: user.admin, не user.current

Проверили через `ApiCallLog` (добавлен для модерации Маркетплейса, ADR-021) реальный ответ
`user.current` для портала `it-wizards.bitrix24.ru`: в JSON нет поля `ADMIN` вообще — не
`false`, а отсутствует как ключ. Значит `me.ADMIN === true` в `syncCurrentUser` всегда было
`false`, для абсолютно любого пользователя, включая настоящих администраторов портала. Из-за
этого при первой реальной установке владелец портала получал роль EMPLOYEE и не видел
«Настройки», «Статьи», «История», «Тарифы», не мог создать проект или назначить роли — и
не мог сам это исправить, потому что доступ к «Настройки» требует уже иметь роль ADMIN.

По документации (apidocs.bitrix24.ru, «Версии скоупа user») поле `ADMIN` не входит ни в один
из трёх уровней `user.*` (`user_brief`, `user_basic`, `user`) — его там в принципе нет.
Признак администратора отдаёт отдельный метод `user.admin` (скоуп «базовый», без
дополнительных прав, `result: true/false` напрямую) — по документации совпадает с полем
`ADMIN` метода `profile`.

`syncCurrentUser` теперь вызывает `user.current` и `user.admin` параллельно (`Promise.all`,
тем же токеном — портальным или разовым пер-юзерным, как и раньше) и берёт `isAdmin` из
`user.admin`. `BitrixCurrentUser.ADMIN` убрано из типа. Тест на реальную форму ответа
Bitrix (без поля `ADMIN` в `user.current`) — регрессия именно на этот случай.

## ADR-026 — Источники импорта проектов из CRM: не только Сделки и Компании

Жёсткая привязка "проект = Сделка (entityTypeId 2) или Компания (4)" не подходит всем
клиентам: на живом портале `it-wizards.bitrix24.ru` (изучен по хуку, который клиент дал для
чтения) проекты ведутся через смарт-процессы — например «Заявки BK» и «Работа по проектам»
(entityTypeId ≥ 1000). `crm.item.*` у Bitrix24 уже устроен универсально — один и тот же метод
работает для Сделки, Компании и любого смарт-процесса по одному параметру `entityTypeId`, —
проблема была только в том, что приложение сверху жёстко ограничивало это двумя значениями
(`.refine((n) => n === 2 || n === 4, …)` в DTO и `? 'COMPANY' : 'DEAL'` при сохранении проекта,
где всё, что не Компания, молча становилось Сделкой).

Решение: новая таблица `CrmImportSource` (миграция `20260922170000_crm_import_source`) хранит
per-portal список смарт-процессов, которые админ явно добавил как источник проектов. Сделки и
Компании остаются встроенными и доступны всегда, без настройки (`BUILTIN_SOURCES` в
`src/server/services/crm-sources.ts`) — это сохраняет "из коробки работает без единой настройки"
для клиентов, у которых проекты — это сделки или компании, как и раньше. `crm.type.list`
(`listSmartProcessTypes`, фильтр `entityTypeId >= 1000`) даёт админу список реально
существующих на портале смарт-процессов для выбора на странице «Источники импорта из CRM»
(`/settings/crm-sources`) — не угадывание кода вручную.

Каждая точка входа проверяет entityTypeId против сконфигурированных источников, а не доверяет
произвольному числу от клиента: и `GET /api/crm` (браузинг перед импортом), и
`POST /api/projects` (сам импорт) — оба бросают `badRequest`, если entityTypeId не встроенный
и не добавлен явно. `Project.crmEntityType` получил третье значение `SMART_PROCESS` (enum уже
предвосхищал это), резолвится по `entityTypeId` (COMPANY/DEAL/иначе SMART_PROCESS), а не по
магическому сравнению с `4`. `getCrmItem` обобщён — резолвинг имени клиента через `companyId`
теперь работает для любого entityTypeId с этим полем, не только для Сделок (проверено на
«Заявки BK», где `companyId` тоже заполнен).

## ADR-027 — Автоматизация расходов по часам: задачи Битрикс24 → черновик → подтверждение

Клиент попросил продумать автоматизацию по трём независимым направлениям: расход по часам
сотрудников, статистика продаж по воронкам, автодоход по проекту из CRM. Начали с первого —
он даёт наибольшую пользу быстрее всего и уже был частично предусмотрен в модели
(`FinancialEntry.calculationMode = HOURS_RATE` с полями `hours`/`hourlyRate` существовал, но
заполнялся только вручную).

Решения (согласованы с клиентом через уточняющие вопросы, без дальнейшего утверждения —
явно сказано "делай не спрашивай меня"):

1. **Источник времени на старте — задачи Битрикс24** (`task.elapseditem.getlist`), а не
   календарь и не отдельный смарт-процесс — их можно добавить позже по тому же принципу, что
   и смарт-процессы для CRM-источников (ADR-026). Задача привязывается к проекту через то же
   поле `UF_CRM_TASK`, которым Битрикс24 линкует задачу к CRM-элементу — то есть автоматизация
   работает только для проектов с `sourceType = BITRIX_CRM` (есть `crmEntityTypeId`/`crmEntityId`
   для сопоставления). Ручные проекты её не получают — осознанное ограничение, не пропуск.
2. **Ставка — одна на сотрудника** (`AppUser.hourlyRate`, задаётся админом в Настройках →
   Команда), не по роли и не по проекту — самый простой вариант, который клиент подтвердил.
3. **Черновик, не сразу расход.** Новая таблица `TaskTimeDraft` (portalId, projectId,
   employeeId, workDate, hours, bitrixTaskIds, status PENDING/APPROVED/REJECTED,
   resultingEntryId) — ночной синк пишет туда, а не напрямую в `FinancialEntry`, чтобы не
   нарушать правило "PLAN/FACT — единственные настоящие строки" (см. CLAUDE.md, правило 5).
   Менеджер подтверждает на странице «Часы к подтверждению» (`/time-drafts`) — только тогда
   создаётся реальная `FinancialEntry` (EXPENSE/FACT/HOURS_RATE) через существующую доменную
   формулу `hoursRateAmount` (единственное место, где считается сумма по часам — не
   продублировано). Отклонённый черновик не блокирует дату навсегда: следующий синк может
   заново предложить её, если время по-прежнему числится в задаче — REJECTED это "пока нет",
   а не "никогда".
4. **APPROVED черновик синк никогда не трогает** — сумма уже стала реальным расходом, только
   ручное редактирование самой `FinancialEntry` может её изменить, автоматика больше не лезет.
5. **Синк = защищённый секретом эндпоинт, не фоновый процесс.** В приложении не было вообще
   никакого cron — вместо долгоживущего процесса внутри Next.js добавлен
   `POST /api/internal/sync-hours`, проверяющий заголовок `x-sync-secret` против
   `INTERNAL_SYNC_SECRET`; дёргается системным cron на VPS раз в сутки. Тот же паттерн
   "секрет сервер-сервер, не пользовательская сессия", что уже был у
   `SUPPORT_BITRIX_WEBHOOK_URL`.
6. **Ошибка на одном проекте не рушит весь синк** — try/catch на уровне проекта внутри
   `syncPortalHours`, ошибка попадает в `result.errors`, остальные проекты синкуются дальше.
7. **Синк идёт только для портов на Pro** (`effectivePlan(portal) === 'PRO'`), не демо и не
   отключённых — избегаем оплаты бесплатным порталам того, что фактически является
   продолжением платного импорта из CRM (ADR-026).

**Осознанный технический риск, требующий проверки на живом портале перед общим релизом**:
формат привязки `UF_CRM_TASK` для смарт-процессов (`T{entityTypeId}_{id}`, например
`"T1068_7"`) взят по аналогии с известным префиксным паттерном Битрикс24 (`D_` сделка, `CO_`
компания), но НЕ подтверждён вызовом к реальному порталу — в отличие от остальной части этой
сессии, где я всегда проверял формат ответа через реальный хук клиента. `crmTaskBinding()`
(`src/lib/bitrix/tasks.ts`) — единственное место, которое нужно будет поправить, если формат
окажется другим; при неверном префиксе `tasks.task.list` просто вернёт пустой список задач
(не ошибку) — синк для такого проекта просто не найдёт часов, не сломается. Прежде чем
показывать эту функцию клиенту как рабочую, стоит один раз проверить на реальном порту с
реальной задачей, привязанной к смарт-процессу.

**Подтверждено на реальном портале сразу после деплоя**: первый прогон `/api/internal/sync-hours`
против `it-wizards.bitrix24.ru` упал с «The request requires higher privileges than provided by
the access token» — у OAuth-токена приложения нет скоупа `task`/`tasks`, только `crm`. Синк не
сломался (сработал fail-soft из пункта 6), но реально часы собирать не может, пока в настройках
Local Application на стороне Битрикс24 не добавлен нужный скоуп и портал не переавторизован —
это ручное действие вне кода, следующий шаг перед тем, как показывать функцию клиенту.

## ADR-028 — Автодоход по проекту: сумма сделки из CRM, а не ручной ввод

Второе из трёх направлений автоматизации (после часов, ADR-027) — клиент прямо сказал не
вписывать доход по проекту руками, тянуть из Битрикс24. В отличие от часов, сумма сделки —
не накопительная величина (не "сколько нового дохода произошло"), а ТЕКУЩЕЕ состояние одного
числа (`opportunity` — то же поле, которое уже возвращает `crm.item.get`/`crm.item.list`,
просто раньше не выбиралось). Это определило другую модель черновика:

1. **Одна строка `CrmIncomeDraft` на проект** (уникальность `portalId+projectId`), не одна на
   событие. Ночной синк (`syncPortalIncome`, `src/server/services/income-sync.ts`) не трогает
   черновик, если сумма в Битриксе не изменилась — вне зависимости от статуса. Если сумма
   изменилась — черновик переоткрывается в PENDING, ДАЖЕ ЕСЛИ он уже был APPROVED: прежнее
   решение относилось к другому числу, показывать его как актуальное было бы неверно.
2. **Одобрение создаёт/правит ОДНУ PLAN-строку дохода**, а не новую при каждом одобрении —
   `resultingEntryId` на черновике запоминает, какую именно `FinancialEntry` править дальше.
   Сумма сделки, выросшая после переговоров, — это правка ожидаемого дохода, а не вторая
   строка дохода по тому же проекту.
3. **Только PLAN, никогда не FACT автоматически.** Это осознанное ограничение объёма, а не
   недосмотр: «когда доход становится реальным (по стадии сделки? по факту оплаты? по
   поступлению на счёт?)» — вопрос, ответ на который зависит от конкретного процесса продаж
   клиента и который нельзя безопасно угадать (нарушение правила №1 CLAUDE.md — «Financial
   correctness first» — было бы худшей ошибкой, чем не построить эту часть вообще). PLAN
   безопасен: он никогда не заявляет, что деньги уже получены.
4. **UI объединён с часами** на одной странице `/automation` (было `/time-drafts`, переименовано,
   т.к. ещё ни одного реального черновика часов в проде не существовало на момент переименования —
   миграция страницы, не данных) — оба раздела решают одну и ту же задачу «проверить и подтвердить
   то, что предложил синк», разносить их по разным пунктам меню не было смысла.
5. **Отдельный эндпоинт `/api/internal/sync-income`**, не совмещён с `/api/internal/sync-hours` —
   разные точки отказа (один синк не должен падать из-за скоупа/лимита другого), отдельная запись
   в crontab.
6. Те же гарантии, что и в ADR-027: синк только для PRO/не-демо/подключённых порталов, ошибка на
   одном проекте не рушит остальные, категория дохода выбирается человеком при подтверждении (не
   угадывается автоматически).

## ADR-029 — Статистика продаж по воронкам: read-only снепшот, без черновиков

Третье, последнее из трёх направлений автоматизации. В отличие от ADR-027/028, эта фича ничего
не пишет в финансы проекта — она вообще не привязана к конкретным проектам приложения, а
показывает портфель сделок портала целиком, сгруппированный по воронке (Bitrix "категория"
сделки) и статусу (выиграно/проиграно/в работе). Это то, что позволяет клиенту увидеть
"первичные продажи" и "абонентское обслуживание" (у него это разные воронки) раздельно, вместо
одной слитной цифры по всем сделкам.

1. **Никакого черновика/подтверждения** — это отчёт, не мутация денег, поэтому нет причины
   городить PENDING/APPROVED, как для часов и дохода. Ночной синк (`syncPortalSalesFunnels`,
   `src/server/services/sales-funnel-sync.ts`) напрямую перезаписывает `SalesFunnelSnapshot`
   (по одной строке на пару воронка+статус), включая удаление строк, для которых сделок больше
   не осталось — отчёт никогда не показывает число, за которым уже нет ни одной сделки.
2. **Классификация статуса по конвенции ID стадии**, не по отдельному запросу
   `crm.dealcategory.stage.list` за семантикой каждой стадии: базовая воронка использует голые
   `WON`/`LOSE`, именованные — `C{id}:WON`/`C{id}:LOSE` (`classifyDealStage` в
   `src/lib/bitrix/deals.ts`). Это устойчивая конвенция Bitrix24 (код стадии не меняется при
   переименовании её заголовка), но не гарантия API — задокументировано в коде как таковое,
   по аналогии с `crmTaskBinding` в ADR-027.
3. **Полная пагинация по всем сделкам портала** (`fetchAllDeals`) — `crm.item.list` не отдаёт
   `total`/`next` через существующий `callBitrix` (он их отбрасывает), пагинация идёт по
   признаку "страница короче 50 — это последняя". Изначальный потолок в 100 страниц (5000
   сделок) оказался МАЛ на практике: первый реальный прогон на it-wizards упёрся именно в него
   (`truncated: true`, 5000 из явно бóльшего числа сделок). Переписано на `batchBitrix` — до 50
   страниц (2500 сделок) за один HTTP-запрос вместо одного запроса на 50 сделок — и потолок
   поднят до 400 батчей (1 000 000 сделок), что при батчинге остаётся посильным для ночной
   задачи. Портал, упёршийся даже в это, получит `truncated: true` в результате синка (не тихую
   неполную цифру) — сигнал, что для такого масштаба нужна другая стратегия (по датам,
   инкрементально), не полный перебор каждую ночь.
4. **Отдельный третий эндпоинт `/api/internal/sync-sales-funnels`** и третья запись в crontab —
   тот же принцип изоляции отказов, что и между sync-hours/sync-income (ADR-027/028).
5. Страница `/sales-funnels` закрыта тем же гейтом Pro, что графики и импорт из CRM (`UpsellNotice`,
   см. ADR-022) — это тоже аналитика поверх Bitrix24-данных, не базовый бесплатный сценарий.

## ADR-030 — /api/bitrix/install тоже должен уметь принимать события Bitrix24

Найдено при живой диагностике попытки переустановки it-wizards.bitrix24.ru (после добавления
scope `task` для ADR-027): в nginx-логах — регулярные `POST /api/bitrix/install` с 400 от
User-Agent «Bitrix24 Webhook Engine», без Referer, не от браузера. После добавления логирования
реальной причины (раньше `catch` сворачивал любую не-`AppError` ошибку в generic «Install
failed» без единой строки в логах — тоже был баг, чинится тем же коммитом) — оказалось:
`Error: Install payload missing member_id / DOMAIN`.

Причина: карточка приложения в кабинете разработчика для типа «rest-only» имеет только ОДНО
поле — «Ссылка на обработчик события установки» — и Bitrix24 шлёт туда ЛЮБОЕ событие жизненного
цикла приложения (включая `ONAPPUNINSTALL`), не только собственно установку. Отдельного URL под
события (тот, что регистрируется программно через `event.bind` в `bindUninstallEvent` и должен
бить в `/api/bitrix/events`) эта конфигурация, видимо, не использует — или использует, но
Bitrix всё равно продолжает слать события и на install-URL тоже. Раньше `/api/bitrix/install`
предполагал, что каждый POST — это либо реальная установка, либо переоткрытие локального
приложения (см. комментарий в файле) — событийный payload (`event`, `auth[...]`, `data[...]`,
без `member_id`/`DOMAIN` на верхнем уровне) не подходил ни под одно из двух и падал в общий catch.

Практическое следствие бага: очистка данных при удалении приложения (`data[CLEAN]=1`, ADR-021)
могла не срабатывать для порталов с такой конфигурацией — уведомление об удалении просто
терялось в 400-й ошибке.

Решение: общая логика обработки событий вынесена в `src/lib/bitrix/events.ts`
(`handleBitrixEvent`), переиспользуется и в `/api/bitrix/events` (как раньше), и в
`/api/bitrix/install` — там теперь в самом начале POST-обработчика проверяется наличие поля
`event` в payload; если оно есть, запрос обрабатывается как событие (и в этом случае никогда
не доходит до `upsertPortalFromInstall`), если нет — как обычно, установка/переоткрытие.

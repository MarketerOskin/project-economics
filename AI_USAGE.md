# Использование ИИ

Приложение разработано с активным использованием ИИ-ассистента (Claude Code). Ниже —
честный разбор: что делал ИИ, что решал и проверял человек, какие потенциальные ошибки
ИИ ловились и чем именно.

## Что разрабатывалось с помощью ИИ

- Каркас проекта, конфигурация (Next 16, TS strict, Tailwind v4, Vitest, Playwright,
  Docker multi-stage).
- Prisma-схема (7 моделей, enum'ы, индексы), первая миграция.
- Чистый движок финансов (`src/domain/finance/`) и его тесты.
- Слой `route()` + `withPortal` + `permissions` + маппинг ошибок.
- Все API-обработчики (проекты, финансы, статьи, дашборд, аудит, Bitrix).
- Интеграция Bitrix24: крипто токенов, REST-клиент с refresh, install/handler,
  синхронизация сотрудников, CRM-браузер.
- Весь UI (компоненты, страницы, графики, формы).
- Демо-сид, документация, скрипт скриншотов.

## Что решал и контролировал человек

- **Интерпретация ТЗ** — приоритеты (корректность финансов > сохранность > безопасность >
  функции > UX > визуал), где идти строго по ТЗ, где выбрать «надёжное простое
  production-решение».
- **Ключевые архитектурные развилки** (см. `docs/DECISIONS.md`): Prisma 6 вместо 7
  (7-ка ломала загрузку `.env`), stateless-сессия вместо таблицы, `typedRoutes` off,
  committed light theme, `prisma` в `dependencies` ради миграций в контейнере.
- **Модель безопасности**: роль всегда из БД, не из cookie; токены Bitrix шифруются и не
  логируются; каждый запрос скоупится `portalId`; CSRF double-submit; rate-limit.
- **Проверка каждой фазы**: `lint` + `typecheck` + `test` + `build` после каждого блока,
  визуальная проверка в браузере (dashboard, роли, формы, CRM-импорт), реальный прогон
  Docker-стека с чистого volume.

## Потенциальные ошибки ИИ, которые проверялись — и чем

| Риск | Как проверено |
|---|---|
| Деление на ноль в рентабельности → `Infinity`/`NaN`/`0%` | `margin()` возвращает `null`, тесты `calculations` + `aggregates`; в UI `—` |
| Потеря точности `Decimal` (`0.1 + 0.2`) | тесты `money` (unit), `schema` (уровень БД), decimal-кейс в `aggregates` |
| Отрицательная прибыль / убыток | кейсы −200 000 / −40% в `calculations`, состояние «убыточный проект» в `seed` |
| PLAN и FACT «протекают» друг в друга | отдельные записи + тест независимости в `aggregates` и `finance/api` |
| Удалённая операция всё ещё в агрегатах | единая точка фильтрации `live()`, тесты `aggregates` + `finance/api` (delete → пересчёт) |
| Клиент присылает произвольную сумму для HOURS_RATE | сервер пересчитывает `часы × ставка`, тест `finance/api` (`amount: 1` → сохранено `200000`) |
| Обход прав на фронтенде | все `can.*` повторно проверяются в `route()`; тесты матрицы §66; **подделанный ADMIN-cookie для EMPLOYEE → 403** |
| Пользователь портала A читает проект портала B по id | `withPortal` + тест `with-portal` (→ 404), тест `projects/api` (cross-portal) |
| Мутация записалась, а audit — нет | всё в одном `$transaction`; тест `projects/atomicity` (падение audit откатывает проект) |
| Токен Bitrix утёк в лог / ответ | `redactTokens` + тест «в логах нет подстроки токена»; тест `security` «ни один ответ не содержит сохранённый токен» |
| N+1 на дашборде | один запрос операций; тест `dashboard` — ≤ 4 SELECT при 8 проектах |
| Сырой JSON аудита показан пользователю | `humanizeAudit` + тесты; тест `audit` проверяет отсутствие `"before":` в ответе |
| Редактирование операции ломает дату | найден баг (`Date.toString()` вместо ISO в `toInitial`) — **обнаружен E2E-тестом ТЗ §67**, исправлен |
| Docker-образ не поднимается с чистой БД | реальный прогон `docker compose down -v && up` — миграция `init` применяется, seed отрабатывает, healthcheck зелёный |

## Тесты, подтверждающие корректность

32 файла, 186 unit/integration + 2 E2E. Разбивка — `docs/TESTING.md`. Ключевое: все 8
кейсов ТЗ §65, вся матрица §66, полный сценарий §67, атомарность §52, отсутствие N+1
§53, изоляция порталов §54.

## Чего в этом файле нет

Здесь не заявлено ничего, что не проверялось. Не проверено вживую (нет доступа к
реальному порталу): фактический OAuth-хендшейк с Bitrix24 и вызовы `crm.item.*` против
живого портала — реализация сделана строго по актуальной REST-документации, покрыта
юнит/интеграционными тестами с замоканным `fetch` и demo-фолбэком, но не прогонялась на
настоящем Bitrix24.
